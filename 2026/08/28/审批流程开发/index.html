审批流程引擎开发实践

从 CRUD Boy 到流程引擎开发者的踩坑实录

之前做后端功能开发，大多是些 CRUD 或者接口聚合的 BFF 层工作，这次遇到审批流程这种相对复杂的场景，特地记录下整个开发过程，希望能给遇到类似需求的同学一些参考。

一、需求分析

核心需求梳理出来有三点：

  1. 多级审批 + 前置依赖：后续节点必须等前置条件满足后，才能变为可审批状态
  2. 流程可配置：变更审批流程时，尽量避免修改代码
  3. 多类型支持：不同的审批类型（如产品线变更、合同审批）需要走不同的流程链路

基于第 2、3 点，我们需要一个审批模板表来存储流程定义，方便后续调整。

二、表结构设计

2.1 三张核心表

整个审批模块由三张表构成，各司其职：

表名 职责 类比
模板表 存储审批流程的”图纸”（节点定义 + 前置规则） 生产线设计图
申请主表 记录一次申请的概要信息（申请人、参数、整体状态） 工单卡片
申请子表 记录该申请下每个节点的运行状态（审批人、意见、时间） 流水线各工位记录

2.2 模板表

字段 类型 说明
申请类型 string 如：产品线变更、合同审批
节点 string 节点标识，按 node_01, node_02… 规则命名
前置条件 json AST 表达式，满足后当前节点才会激活
状态 enum 待审批 / 审批中 / 已通过 / 已退回 / 已驳回
审批人 string 该节点的审批人标识

2.3 申请主表

字段 类型 说明
id string 主键
申请类型 string 关联模板
申请人 string 谁发起的
摘要 string 一句话说明
参数 json 业务参数（如：新负责人、产品线名称），供审批通过后执行变更
审批状态 enum 整个申请的聚合状态
附件 string 附件信息

为什么需要主表？

  • 统一状态存储：审批流程可能有分支，并非所有节点都会走到。如果按”所有节点都通过”来判断流程结束，在有分支的场景下会很麻烦。主表单独维护一个聚合状态，查询时 O(1) 就能知道申请状态。
  • 参数与摘要隔离：业务参数（如变更内容）属于整个申请，没必要在每个节点都存一份，放在主表更合理。

2.4 申请子表

字段 类型 说明
id string 主键
mainId string 关联主表
节点 string 对应模板中的节点标识
状态 enum 当前节点状态
审批人 string 谁负责审批
前置条件 json 从模板复制过来的规则（用于引擎计算）
审批意见 string 审批人填写的意见
附件 string 审批附件

发起申请时的流程：

  1. 申请人提交 → 主表新增一条记录
  2. 触发器/后台任务根据申请类型从模板表复制节点定义 → 插入子表（所有节点初始状态为”待审批”）
  3. 引擎根据前置条件自动计算第一个可激活的节点 → 状态变为”审批中” → 发送通知给审批人
  4. 审批人操作 → 引擎级联更新后续节点状态 → 直到流程结束

三、前置条件系统（AST 表达式）

3.1 为什么需要 AST？

前置条件的常见形式：

  • 节点依赖：node_01 审批通过后，node_02 才能开始
  • 表单条件：金额 > 10000 时走总监审批，否则跳过
  • 组合条件：（部门经理通过 AND 金额 > 50000）OR 总监特批

如果用字符串模板或硬编码，后期维护会非常痛苦。所以采用 AST（抽象语法树） 来结构化存储条件。

六、一个细节：为什么不能只靠 changes 判断流程结束？

最初我尝试用 changes.length === 1 或 changes.some(r => r.newStatus === 'PROCESSING') 来判断流程是否结束，但都存在问题。

考虑这个分支依赖场景：

用户审批通过 node_01 后：

此时 result.changes 里没有 PROCESSING，但 node_03 还等着审批，流程远未结束。

因此，propagateStatusChange 返回 isFinished 字段：它遍历引擎持有的所有节点（包括状态没变的 node_03），只有全部达到终态（PASSED / RETURNED / REJECTED / SKIPPED）时才返回 true。

这就是为什么业务接口只需要检查 result.isFinished，而不是自己分析 changes。

七、总结

按上述思路，我们实现了一个具有灵活前置条件配置的审批流引擎，核心收获有几点：

  1. 模板与实例分离：模板负责定义流程蓝图，实例负责记录运行时状态，变更模板不影响正在运行的审批。

  2. AST 表达式系统：将前置条件从代码中抽离出来，以结构化 JSON 存储。引擎只负责解析和执行，业务人员可通过配置界面修改规则，无需重新发版。

  3. 级联状态传播：节点状态变化后，引擎自动计算所有下游节点的新状态，并将变更列表一次性返回给调用方。

  4. engine 返回 isFinished：引擎基于所有节点的终态计算 isFinished，避免了调用方自行分析 changes 时在分支依赖场景下的误判。

  5. 主表聚合状态：配合主表存储审批状态，业务层可 O(1) 查询申请是否结束，无需每次都跑引擎计算。
