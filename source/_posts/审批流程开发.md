# 审批流程引擎开发实践

> 从 CRUD Boy 到流程引擎开发者的踩坑实录

之前做后端功能开发，大多是些 CRUD 或者接口聚合的 BFF 层工作，这次遇到审批流程这种相对复杂的场景，特地记录下整个开发过程，希望能给遇到类似需求的同学一些参考。


## 一、需求分析

核心需求梳理出来有三点：

1. **多级审批 + 前置依赖**：后续节点必须等前置条件满足后，才能变为可审批状态
2. **流程可配置**：变更审批流程时，尽量避免修改代码
3. **多类型支持**：不同的审批类型（如产品线变更、合同审批）需要走不同的流程链路

基于第 2、3 点，我们需要一个**审批模板表**来存储流程定义，方便后续调整。


## 二、表结构设计

### 2.1 三张核心表

整个审批模块由三张表构成，各司其职：

| 表名 | 职责 | 类比 |
| :--- | :--- | :--- |
| **模板表** | 存储审批流程的"图纸"（节点定义 + 前置规则） | 生产线设计图 |
| **申请主表** | 记录一次申请的概要信息（申请人、参数、整体状态） | 工单卡片 |
| **申请子表** | 记录该申请下每个节点的运行状态（审批人、意见、时间） | 流水线各工位记录 |

### 2.2 模板表

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| 申请类型 | string | 如：产品线变更、合同审批 |
| 节点 | string | 节点标识，按 `node_01`, `node_02`... 规则命名 |
| 前置条件 | json | AST 表达式，满足后当前节点才会激活 |
| 状态 | enum | 待审批 / 审批中 / 已通过 / 已退回 / 已驳回 |
| 审批人 | string | 该节点的审批人标识 |

### 2.3 申请主表

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| id | string | 主键 |
| 申请类型 | string | 关联模板 |
| 申请人 | string | 谁发起的 |
| 摘要 | string | 一句话说明 |
| 参数 | json | 业务参数（如：新负责人、产品线名称），供审批通过后执行变更 |
| 审批状态 | enum | 整个申请的聚合状态 |
| 附件 | string | 附件信息 |

**为什么需要主表？**

- **统一状态存储**：审批流程可能有分支，并非所有节点都会走到。如果按"所有节点都通过"来判断流程结束，在有分支的场景下会很麻烦。主表单独维护一个聚合状态，查询时 O(1) 就能知道申请状态。
- **参数与摘要隔离**：业务参数（如变更内容）属于整个申请，没必要在每个节点都存一份，放在主表更合理。

### 2.4 申请子表

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| id | string | 主键 |
| mainId | string | 关联主表 |
| 节点 | string | 对应模板中的节点标识 |
| 状态 | enum | 当前节点状态 |
| 审批人 | string | 谁负责审批 |
| 前置条件 | json | 从模板复制过来的规则（用于引擎计算） |
| 审批意见 | string | 审批人填写的意见 |
| 附件 | string | 审批附件 |

**发起申请时的流程**：

1. 申请人提交 → 主表新增一条记录
2. 触发器/后台任务根据申请类型从模板表复制节点定义 → 插入子表（所有节点初始状态为"待审批"）
3. 引擎根据前置条件自动计算第一个可激活的节点 → 状态变为"审批中" → 发送通知给审批人
4. 审批人操作 → 引擎级联更新后续节点状态 → 直到流程结束


## 三、前置条件系统（AST 表达式）

### 3.1 为什么需要 AST？

前置条件的常见形式：

- **节点依赖**：`node_01` 审批通过后，`node_02` 才能开始
- **表单条件**：金额 > 10000 时走总监审批，否则跳过
- **组合条件**：（部门经理通过 AND 金额 > 50000）OR 总监特批

如果用字符串模板或硬编码，后期维护会非常痛苦。所以采用 **AST（抽象语法树）** 来结构化存储条件。

### 3.2 类型定义

```typescript
// 节点类型
export type AstType = 'AND' | 'OR' | 'NOT' | 'LEAF';
export type LeafKey = 'NODE_STATUS' | 'FORM_FIELD';
export type Operator = '==' | '!=' | '>' | '<' | '>=' | '<=' | 'in';

// 引擎内部状态
export type EngineStatus =
  | 'PENDING'     // 待审批
  | 'PROCESSING'  // 审批中
  | 'PASSED'      // 已通过
  | 'RETURNED'    // 已退回
  | 'REJECTED'    // 已驳回
  | 'BLOCKED'     // 阻塞中
  | 'SKIPPED';    // 已跳过

// AST 节点定义
export interface AstNode {
  type: AstType;
  children?: AstNode[];   // AND / OR 使用
  child?: AstNode;        // NOT 使用
  key?: LeafKey;          // LEAF 使用
  nodeId?: string;        // NODE_STATUS 时使用
  expected?: EngineStatus | EngineStatus[];
  field?: string;         // FORM_FIELD 时使用
  value?: string | number | boolean | any[];
}
```

### 3.3 前置条件示例

**单个节点依赖：判断 node_01 是否已通过**

```json
{
  "type": "LEAF",
  "key": "NODE_STATUS",
  "nodeId": "node_01",
  "expected": "PASSED"
}
```

**分支判断：部门属于指定列表**

```json
{
  "type": "LEAF",
  "key": "FORM_FIELD",
  "field": "department",
  "operator": "in",
  "value": ["研发部", "产品部", "设计部"]
}
```

**复杂组合：（A AND B）OR （金额>10000 AND C）**

```json
{
  "type": "OR",
  "children": [
    {
      "type": "AND",
      "children": [
        { "type": "LEAF", "key": "NODE_STATUS", "nodeId": "node_A", "expected": "PASSED" },
        { "type": "LEAF", "key": "NODE_STATUS", "nodeId": "node_B", "expected": "PASSED" }
      ]
    },
    {
      "type": "AND",
      "children": [
        { "type": "LEAF", "key": "FORM_FIELD", "field": "amount", "operator": ">", "value": 10000 },
        { "type": "LEAF", "key": "NODE_STATUS", "nodeId": "node_C", "expected": "PASSED" }
      ]
    }
  ]
}
```

### 3.4 FORM_FIELD 的 value 如何传入？

`FORM_FIELD` 的 `value` 是通过引擎运行时的 `context.formData` 传入的：

```typescript
const result = engine.propagateStatusChange('node_01', 'PASSED', {
  formData: {
    amount: 15000,      // 对应 AST 中的 field: "amount"
    department: '研发部' // 对应 AST 中的 field: "department"
  }
});
```

引擎内部会从 `context.formData` 中根据 `field` 取值，再与 AST 中的 `value` 进行比较。


## 四、审批引擎实现

### 4.1 引擎核心能力

```typescript
export class ApprovalStateEngine {
  // 核心方法：修改某个节点状态，自动级联影响所有下游节点
  public propagateStatusChange(
    nodeId: string,
    newStatus: EngineStatus,
    extraContext?: { formData: Record<string, unknown> }
  ): {
    changes: StatusChangeItem[];   // 状态发生变化的节点列表
    isFinished: boolean;           // 流程是否已结束
  }
}
```

**入参**：
- `nodeId`：要修改状态的节点 ID
- `newStatus`：目标状态（如 `'PASSED'`）
- `extraContext.formData`：表单数据（用于 `FORM_FIELD` 条件判断）

**返回值**：

```typescript
interface StatusChangeItem {
  nodeId: string;        // 受影响的节点 ID
  oldStatus: EngineStatus;
  newStatus: EngineStatus;
  reason?: string;       // 变更原因（如"前置条件已满足，进入审批中"）
  node: EngineNode;      // 完整节点对象（含名称、审批人等）
}
```

- `changes`：所有状态发生变化的节点列表
- `isFinished`：流程是否已结束（基于引擎内部所有节点状态计算）

### 4.2 级联状态传播核心实现

引擎内部通过以下流程完成级联更新：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        propagateStatusChange 核心流程                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  1. 更新目标节点状态（如 node_01: PENDING → PASSED）                        │
│                         ↓                                                   │
│  2. 构建依赖图（从 AST 中提取所有 nodeId 引用）                             │
│                         ↓                                                   │
│  3. 获取所有下游节点（直接或间接依赖于目标节点的节点）                       │
│                         ↓                                                   │
│  4. 按层级排序后迭代计算                                                    │
│       ├── 评估每个节点的前置条件                                            │
│       ├── 条件满足：PENDING/BLOCKED → PROCESSING                           │
│       └── 条件不满足：PENDING/PROCESSING → BLOCKED                         │
│                         ↓                                                   │
│  5. 返回所有受影响节点列表 + isFinished 标志                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

核心代码如下：

```typescript
public propagateStatusChange(
  nodeId: string,
  newStatus: EngineStatus,
  extraContext?: { formData: Record<string, unknown> },
): { changes: StatusChangeItem[]; isFinished: boolean } {
  const targetNode = this.nodeMap.get(nodeId);
  const changes: StatusChangeItem[] = [];

  // 1. 更新目标节点
  const oldStatus = targetNode.status;
  targetNode.status = newStatus;
  changes.push({ nodeId, oldStatus, newStatus, node: targetNode });

  // 2. 构建依赖图，找出所有下游节点
  const depMap = this.buildDependencyMap();          // 从 AST 提取 nodeId 引用
  const downstreamIds = this.getDownstreamNodes(nodeId, depMap);

  // 3. 按层级排序后迭代传播
  const sorted = downstreamIds
    .map(id => this.nodeMap.get(id))
    .sort((a, b) => a.level - b.level);

  let iteration = 0;
  while (iteration < this.nodes.length) {
    let hasChanges = false;
    for (const node of sorted) {
      if (this.isTerminal(node.status)) continue;

      const isReady = this.evaluateAst(node.preConditionJson, {
        statusMap: this.statusMap,
        formData: extraContext?.formData || {},
      });

      let newState: EngineStatus | null = null;
      if (isReady && (node.status === 'PENDING' || node.status === 'BLOCKED')) {
        newState = 'PROCESSING';          // 解锁，进入审批中
      } else if (!isReady && (node.status === 'PENDING' || node.status === 'PROCESSING')) {
        newState = 'BLOCKED';             // 条件不满足，阻塞
      }

      if (newState && newState !== node.status) {
        node.status = newState;
        changes.push({ nodeId: node.id, oldStatus, newStatus: newState, node });
        hasChanges = true;
      }
    }
    if (!hasChanges) break;
    iteration++;
  }

  // 4. 返回变更列表 + 流程是否终结
  const isFinished = this.nodes.every(n => this.isTerminal(n.status));
  return { changes, isFinished };
}
```

**关键设计**：

- `buildDependencyMap()` 遍历所有节点的 AST，提取 `NODE_STATUS` 类型的引用，构建 `被依赖节点 → 依赖它的节点列表` 的映射。
- 按层级排序保证低层级节点先处理（如 node_02 先于 node_03）。
- 外层 `while` 循环用于处理级联唤醒（A 解锁 B，B 又解锁 C），每次迭代都重新评估所有下游节点，直到没有新变化为止。
- `isFinished` 基于引擎持有的**所有节点**计算，包括状态没变化的节点，避免了仅依赖 `changes` 列表在分支依赖场景下的误判。

### 4.3 AST 评估逻辑

```typescript
public evaluateAst(ast: AstNode | null, context: { statusMap, formData }): boolean {
  if (!ast) return true;

  switch (ast.type) {
    case 'LEAF':
      return this.evaluateLeaf(ast, context);
    case 'AND':
      return ast.children.every(child => this.evaluateAst(child, context));
    case 'OR':
      return ast.children.some(child => this.evaluateAst(child, context));
    case 'NOT':
      return !this.evaluateAst(ast.child, context);
    default:
      return true;
  }
}

private evaluateLeaf(leaf: AstNode, context): boolean {
  if (leaf.key === 'NODE_STATUS') {
    const actual = context.statusMap.get(leaf.nodeId);
    const expected = leaf.expected;
    const operator = leaf.operator || '==';
    switch (operator) {
      case '==': return actual === expected;
      case '!=': return actual !== expected;
      case 'in': return (expected as string[]).includes(actual);
      default: return actual === expected;
    }
  }

  if (leaf.key === 'FORM_FIELD') {
    const actual = context.formData[leaf.field];
    const expected = leaf.value;
    switch (leaf.operator) {
      case '>': return actual > expected;
      case '<': return actual < expected;
      case '>=': return actual >= expected;
      case '<=': return actual <= expected;
      default: return actual == expected;
    }
  }

  return false;
}
```

### 5.2 状态映射

数据库中存储的是数字状态（1~5），引擎内部使用字符串状态，需要在边界做转换：

```typescript
// 数字 → 引擎状态
const STATUS_MAP: Record<number, EngineStatus> = {
  1: 'PENDING',
  2: 'PROCESSING',
  3: 'PASSED',
  4: 'RETURNED',
  5: 'REJECTED',
};

// 引擎状态 → 数字
const REVERSE_STATUS: Record<EngineStatus, number> = {
  'PENDING': 1,
  'PROCESSING': 2,
  'PASSED': 3,
  'RETURNED': 4,
  'REJECTED': 5,
  'BLOCKED': 1,  // 阻塞对外显示为"待审批"
};
```

### 5.3 节点适配：数据库主键 vs 业务节点标识

在"回退重提"场景下，两轮节点可能拥有相同的 `jiedian`（如 `node_01`），需要用数据库主键作为引擎的唯一标识：

## 六、一个细节：为什么不能只靠 changes 判断流程结束？

最初我尝试用 `changes.length === 1` 或 `changes.some(r => r.newStatus === 'PROCESSING')` 来判断流程是否结束，但都存在问题。

考虑这个分支依赖场景：

```
节点 2 依赖：node_01 PASSED AND node_03 PASSED
```

当前状态：node_01、node_02、node_03 都是 `PENDING`。

用户审批通过 node_01 后：

```typescript
const result = engine.propagateStatusChange('node_01', 'PASSED');

// result.changes = [
//   { nodeId: 'node_01', newStatus: 'PASSED' },
//   { nodeId: 'node_02', newStatus: 'BLOCKED' }   // 因为 node_03 还没过
// ]

// node_03 仍然是 PENDING，但它的状态没变，不会出现在 changes 中！
```

此时 `result.changes` 里没有 `PROCESSING`，但 `node_03` 还等着审批，流程远未结束。

**因此，`propagateStatusChange` 返回 `isFinished` 字段**：它遍历引擎持有的所有节点（包括状态没变的 node_03），只有全部达到终态（`PASSED` / `RETURNED` / `REJECTED` / `SKIPPED`）时才返回 `true`。

这就是为什么业务接口只需要检查 `result.isFinished`，而不是自己分析 `changes`。


## 七、总结

按上述思路，我们实现了一个具有**灵活前置条件配置**的审批流引擎，核心收获有几点：

1. **模板与实例分离**：模板负责定义流程蓝图，实例负责记录运行时状态，变更模板不影响正在运行的审批。

2. **AST 表达式系统**：将前置条件从代码中抽离出来，以结构化 JSON 存储。引擎只负责解析和执行，业务人员可通过配置界面修改规则，无需重新发版。

3. **级联状态传播**：节点状态变化后，引擎自动计算所有下游节点的新状态，并将变更列表一次性返回给调用方。

4. **engine 返回 isFinished**：引擎基于所有节点的终态计算 `isFinished`，避免了调用方自行分析 `changes` 时在分支依赖场景下的误判。

5. **主表聚合状态**：配合主表存储审批状态，业务层可 O(1) 查询申请是否结束，无需每次都跑引擎计算。
